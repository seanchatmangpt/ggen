## HARD PREREQUISITE — `scripts/gate_m2_check.sh` is currently broken (blocking)

A recent audit of `~/beam4pm` found `bash scripts/gate_m2_check.sh` fails on a live run.
The gate's own contract (`~/beam4pm/CLAUDE.md`, Build/sync/test section) is: find every
file carrying the `GENERATED by ggen` marker under
`src, lib, test, gleam/src, gleam/test, schema, docs/reference`, delete exactly those
files, regenerate, and diff — proving ggen is a pure function of
`(ontology.ttl, pack templates)` with no dependency on prior disk state.

The audited failure: the gate's regenerate step invokes both manufacturing engines —
the primary Rust ggen pipeline and the separate Elixir-native `ggen_igniter` engine
(`scripts/igniter_sync.sh`, `mix ggen_igniter.sync`). The `ggen_igniter` leg hit
`build_broken` mid-run: `lib/beam4pm_ash.ex` (the 31 `Ash.Resource` modules
`igniter_sync.sh` manufactures) was deleted by the gate's delete-then-regenerate step
and never recreated, because the `ggen_igniter` regenerate call itself failed after the
delete had already run. The subsequent `mix compile` then threw `File.Error` against
the missing file. This left 320 files / 22,636 lines deleted in the beam4pm working tree
before being manually reverted with `git checkout` — a real, reproducible, currently-live
defect, not a hypothetical one. It was caught and reverted in the session that found it;
it has not been fixed at the root.

**This is a hard prerequisite for this ticket.** None of this ticket's beam4pm-trial
acceptance bullets (below) can be considered satisfied while `gate_m2_check.sh` can
destructively delete 320+ files on a `build_broken` outcome from either manufacturing
engine. Fix requirements:

1. `gate_m2_check.sh`'s delete step must not proceed to delete files for a manufacturing
   engine leg (Rust ggen or `ggen_igniter`) until that leg's regenerate command has been
   dry-run or otherwise confirmed capable of succeeding — or the delete and regenerate
   for each engine must be made atomic (e.g. delete into a staging location, regenerate,
   only commit the delete on regenerate success; or regenerate into a temp directory and
   diff before ever deleting the working-tree copy).
2. A `build_broken` outcome from either engine must leave the working tree unchanged
   (verified by `git status --short` showing zero unexpected deletions), not partially
   deleted.
3. Re-verify with a clean run: `bash scripts/gate_m2_check.sh` exits 0, and
   `git status --short` before and after the run are identical (nothing to revert).

## Background (approved plan context — not re-derived)

Real exploration across `~/ggen`, `~/ggen-marketplace`, `~/ggen_igniter`, `~/beam4pm`
established three findings that this ticket set works around rather than solves at the
root:

1. ggen has no pack-to-pack composition/dependency mechanism. `pack.toml`'s schema is
   closed (`deny_unknown_fields`; only `[pack]` with name/version/description —
   `ggen-engine/src/pack.rs` lines 70-93). A `PackComposer`/`DependencyGraph` subsystem
   exists in `ggen-marketplace::packs_registry` (`composer.rs`, `dependency_graph.rs`)
   but is dead code, unreachable from any CLI verb. Zero of the ~150-207 packs in the
   corpus use a `[dependencies]` table. The formal composition algebra
   (`docs/thesis/09-pack-algebra.md` in `~/ggen-marketplace`) is aspirational design
   work, not a built mechanism.
2. Two of the four fortune5-adjacent packs are hardcoded to ggen-marketplace's own repo
   and are not portable to an arbitrary consumer today:
   `fortune5-required-capabilities-pack` (literal
   `../../../../crates/ggen-marketplace` `Cargo.toml.tmpl` path and real
   `use ggen_marketplace::{...}` calls into a hand-written crate that only exists in the
   `ggen-marketplace` repo) and `fortune5-testing-bblock-pack` (`testing_bblock.py.tmpl`
   auto-detects and tests `crates/ggen-cli/` / `target/debug/ggen` — ggen's own repo, not
   the consumer's project). These two packs must be fixed for portability before or as
   part of this ticket set (tracked elsewhere in this v26.9.1 set); this ticket assumes
   that fix has landed.
3. `ggen_igniter` has real precedent machinery for "one command wires a new capability
   into a consumer project" (`Igniter.Project.Deps.add_dep`,
   `Igniter.Project.Config.configure_new`, `Igniter.Project.Application.add_new_child`,
   and the `Rule` struct codemod engine in `lib/ggen_igniter/doctor_fixes.ex`) but zero
   real `ggen.toml` TOML I/O and zero code that shells out to a real external `ggen sync
   run` today. The new `mix ggen_igniter.fortune5_ready` task supplies both.

`fortune5-architecture-pack` (21 ontology classes, 7 SPARQL gates in
`gates/010-070*.rq`, 4 templates generating `architecture_catalog.md` /
`architecture_dag.dot` / `control_matrix.md` / `workflow_pattern_coverage.md`) and
`fortune5-deployment-blocks-pack` (15 atomic + 4 composite `bb:BlockGroup` individuals
covering aws/azure/gcp, 2 gates, broker-only / no-direct-cloud-actuation by design) were
found portable in the initial exploration pass with no hardcoded external dependency —
but that pass did not test-generate against a fresh scratch consumer project, only
inspected the templates. This ticket's trial against beam4pm is the first live test of
that portability claim.

## Story: run the bundle installer against beam4pm

Work happens in an isolated git worktree/branch inside `~/beam4pm` — **no merge to
`main` without separate explicit confirmation** after this ticket's trial. Use the
`superpowers:using-git-worktrees` pattern or an equivalent `git worktree add`.

Steps:

1. From the isolated worktree, run `mix ggen_igniter.fortune5_ready` (or the task's
   final real name/flags, whatever the implementing ticket lands) against the beam4pm
   project.
2. Confirm `ggen.toml`'s `[packs]` table gains exactly two new entries —
   `fortune5-architecture` and `fortune5-deployment-blocks` — and the existing 5 entries
   (`beam4pm-process-model`, `beam4pm-pro-infra`, `github-actions-pack`,
   `beam4pm-ai-contracts`, `beam4pm-pro-entitlement`) plus the `gh-terraform-pack`
   decline comment are byte-identical to their pre-run state (diff the file, not a
   summary).
3. Run `ggen sync run` for real.
4. Run the now-fixed `bash scripts/gate_m2_check.sh` for real (prerequisite above must
   already be closed) — must exit 0 with zero destructive side effects.
5. Run `fortune5-architecture-pack`'s own gates (`gates/010-070*.rq`) and
   `fortune5-deployment-blocks-pack`'s own 2 gates against the beam4pm-generated output,
   for real, via whatever gate-runner mechanism those packs use (SPARQL ASK/CONSTRUCT
   queries against the synced RDF graph, per the packs' own convention) — not asserted
   from generation success alone.

## What this does and does not close (explicit accounting)

Cross-referenced against beam4pm's own 7-dimension Fortune-5-readiness audit under
`~/beam4pm/docs/jira/v26.8.29/` (security/airgap, architecture documentation, and the
other dimensions that audit enumerates).

**Partial progress, real but bounded:**

- Security/airgap dimension: `fortune5-architecture-pack`'s generated
  `architecture_catalog.md` and `control_matrix.md` give beam4pm real,
  generated-from-ontology architecture documentation and a control matrix — this is
  scaffold/documentation/contract generation (e.g. naming SPIFFE/KMS/observability
  control points in the catalog), not implemented SPIFFE identity issuance, KMS
  integration, or an observability pipeline. The pack generates the contract surface;
  it does not implement the runtime behavior behind it.
- Deployment dimension: `fortune5-deployment-blocks-pack`'s 15 atomic + 4 composite
  block individuals give beam4pm generated deployment-block coverage across
  aws/azure/gcp, broker-only by design (no direct cloud actuation) — this documents and
  scaffolds a deployment topology; it does not deploy anything.

**Explicitly NOT closed by this ticket, stated so "instantly ready" is never
overclaimed once this ships:**

- No cloud marketplace listing (AWS/Azure/GCP Marketplace) is created or touched.
- No SOC2 audit, no pentest, no third-party security certification of any kind is
  performed or claimed.
- No RBAC-scoped Kubernetes runtime code is written; `fortune5-deployment-blocks-pack`
  is broker-only by design and generates no direct cloud/k8s actuation code.
- No OCPM/simulation algorithm gaps are closed — no object-centric Petri net synthesis,
  no discrete-event simulation. Those gaps belong to `beam4pm_pro`'s own roadmap
  (`~/beam4pm/docs/jira/v26.8.29/`) and are untouched by the fortune5 bundle.
- No general ggen-core pack-dependency resolver or pack-composition algebra is built —
  this ticket set works around that gap via the bundle-manifest + installer pattern, it
  does not implement `docs/thesis/09-pack-algebra.md`'s formal design.
- The dead `PackComposer`/`DependencyGraph` Rust subsystem in
  `ggen-marketplace::packs_registry` is not resurrected into a CLI verb.
- Every other gap enumerated in the earlier 7-dimension Fortune-5-readiness audit that
  this ticket's two packs do not directly touch remains open and untouched by this
  ticket.
