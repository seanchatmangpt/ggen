## Verification: act(1) local-container validation

`.github/actions/setup-ggen-build-errc-proposed/action.yml` was run for real inside a
container via `nektos/act` v0.2.87 (2026-08-05), not merely YAML-checked. Two runs are
recorded: an initial minimal-image run that found a real act limitation, and a
follow-up full-image run (this section's authoritative result) that closed it end to
end.

**Environment notes** (properties of this local validation environment, not of the
proposed action):
- Docker was unresponsive by default (stale `docker info` processes); `colima` was
  started for a working daemon, with `--container-daemon-socket -` because act's
  default bind-mount path conflicts with colima's socket location.
- act mirrors the host's absolute checkout path (`/Users/sac/ggen`) inside the
  container without granting the non-root runner user write access to its *parent*
  directory — real GitHub-hosted runners don't have this problem, because
  `$GITHUB_WORKSPACE`'s parent (`/home/runner/work/ggen`) is fully owned by the
  runner user. The validation workflow (not the proposed action) carries a one-line
  act-only compatibility shim (`sudo chmod 777 "$(dirname "$GITHUB_WORKSPACE")"`)
  before invoking the action, to reproduce that same real-CI precondition locally.
- Running the container natively (no forced `--container-architecture linux/amd64`)
  on this Apple-silicon host avoided a slow/space-exhausting cross-arch image pull —
  the earlier `linux/amd64` attempt pulled a second ~35GB image copy and drove the
  colima VM's disk to `no space left on device`. Native `arm64` execution needed no
  emulation and completed cleanly.
