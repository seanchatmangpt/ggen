# ggen Building Blocks Certification Program v26.7.30

## Purpose

The ggen Building Blocks certification program qualifies a person or agent to reconstruct a governed enterprise from executable Building Blocks.

TAI is the canonical case study for every credential level.

It is not a course-completion badge. It is a cumulative evidence program.

```text
historical TAI observation
→ admitted TAI enterprise graph
→ GBB dependency closure
→ generated reconstruction roadmap
→ manufactured architecture capability
→ positive witness + negative falsifier
→ independent verification
→ receipt verification + replay
→ bounded TAI rebuild simulation
→ certification award receipt
```

An external certificate is a receipt that an issuer made an award. It does not, by itself, establish internal capability standing. Internal standing is derived only from admitted evidence.

## Certification calculus

For requirement `q`, a candidate receipt is admissible only when all surfaces are non-empty and bound to the same candidate and requirement:

```text
E(q) = {
  positive witness,
  negative falsifier,
  independent verifier,
  receipt verifier,
  replay
}
```

A level is cumulative:

```text
Award(candidate, level, TAI)
  iff
∀ q where q.level ≤ level: complete(E(q))
```

The award digest binds:

- certification program identity and version;
- canonical TAI case-study identity;
- candidate identity;
- requested level;
- cumulative requirement identities;
- exact requirement-receipt digests.

A receipt from a different case study cannot silently satisfy the TAI award.

## Five cumulative credentials

### GBB-100 — TAI Foundation

**Outcome:** preserve the TAI fence and diagnose the calculus.

The candidate must:

1. distinguish historical observation, target enterprise, and Target Architecture Instance;
2. explain identity, lifecycle, standing, ports, ceilings, obligations, exclusions, provenance, and BRCE authority;
3. map malformed TAI facets to stable refusal codes and bounded repairs.

### GBB-200 — TAI Builder

**Outcome:** manufacture one independently verifiable TAI enterprise facet.

The candidate must:

1. construct a valid block with typed ports, contract, ceilings, exclusions, provenance, and passport-bound realization;
2. close every evidence obligation through all five proof surfaces and derive `ALIVE` mechanically.

### GBB-300 — TAI Composer

**Outcome:** manufacture the enterprise from dependency closure rather than a hand-authored implementation sequence.

The candidate must:

1. compose all nine facets plus the enterprise root;
2. emit deterministic dependency-before-dependent order and the canonical composition receipt;
3. refuse duplicate identities, missing dependencies, cycles, incomplete closure, and incompatible profiles.

### GBB-400 — TAI Governor

**Outcome:** preserve architecture law while realizations and lifecycle change.

The candidate must:

1. assess substitution while preserving outputs, passports, authority, resources, supportability, replacement, and retirement;
2. govern concept-through-decommission lifecycle, evidence standing, and BRCE-addressed intents as distinct states.

### GBB-500 — TAI Manufacturer

**Outcome:** use the TAI Building Blocks as generators of the exact enterprise reconstruction roadmap.

The candidate must:

1. generate the deterministic roadmap from current TAI graph and evidence state;
2. resolve every roadmap step and issue a replay-stable enterprise rebuild receipt;
3. inject one dependency, profile, realization, evidence, replay, or lifecycle failure;
4. recover without bypassing law;
5. manufacture a verifier and falsifier fixture another candidate can replay independently.

## Failure conditions

The candidate fails a requirement when any of these occurs:

- a required proof surface is absent;
- a digest is empty or detached from its requirement or TAI case-study identity;
- a negative fixture is accepted;
- replay changes canonical output;
- authority or resource scope expands;
- mission, quality, lifecycle, evidence, or profile constraints are silently removed;
- a roadmap is hand-authored outside the observed TAI closure;
- the target composition digest drifts;
- a TAI receipt is issued with unresolved roadmap work;
- direct actuation occurs from the architecture kernel.

Certification does not expire merely because time passed. It becomes stale when TAI law, the enterprise graph, or required capability changes materially.

```text
previous TAI requirement closure
+ changed/new requirements or blocks
+ replay of affected prior requirements
→ renewed award receipt
```

Unchanged, replay-stable requirements are not repeated for ceremony.
