# ggen Building Blocks Certification Program v26.7.30

## Purpose

The ggen Building Blocks certification program qualifies a person or agent to reconstruct governed architecture from executable Building Blocks.

It is not a course-completion badge. It is a cumulative evidence program.

```text
credential body of knowledge
→ admitted GBB calculus
→ dependency-closed roadmap
→ manufactured architecture artifacts
→ positive witness + negative falsifier
→ independent verification
→ receipt verification + replay
→ bounded TAI rebuild simulation
→ certification award receipt
```

An external certificate is a receipt that an issuer made an award. It does not, by itself, establish internal capability standing. Internal standing is derived only from admitted evidence.

## Preserve

The program preserves the GBB-000 constitutional boundary:

- lifecycle and evidentiary standing remain orthogonal;
- `RETIRED` is a lifecycle, not a standing;
- `ALIVE` requires positive witness, negative falsifier, independent verifier, receipt verifier, and replay for every declared obligation;
- realizations remain bound to exact Part Passport identities and digests;
- substitution cannot expand authority, resources, or promised-interface loss;
- the architecture kernel remains deterministic, IO-free, and incapable of direct external actuation;
- BRCE remains the only lawful downstream actuation address.

CertificationAssist remains the reusable learning and evidence-manufacturing rail. This program supplies the GBB-specific curriculum, assessment calculus, roadmap generator, and final TAI-rebuild crown.

## Fence

The program certifies capability inside this boundary:

```text
read GBB law
→ diagnose/refuse
→ construct
→ close evidence
→ compose
→ substitute/govern
→ generate roadmap
→ simulate TAI rebuild
→ transfer verifier
```

It does not certify:

- production operation of an unbounded external system;
- vendor-specific product memorization;
- psychometric validity outside the declared fixtures;
- employment readiness for an unspecified role;
- authority to bypass admission, broker, receipt, or replay law;
- real-world `ALIVE` standing merely because source code, documentation, or a badge exists.

## Calculus

### Certification standing

For requirement `q`, a candidate receipt is admissible only when all surfaces are non-empty and bound to the same candidate and requirement:

```text
E(q) = {
  positive witness,
  negative falsifier,
  independent verifier,
  receipt verifier,
  replay
}
```

A level is cumulative:

```text
Award(candidate, level)
  iff
∀ q where q.level ≤ level: complete(E(q))
```

The award digest binds the program identity and version, candidate identity, requested level, cumulative requirement identities, and exact requirement-receipt digests.

### GBB-generated roadmap

The roadmap is not written before observing the target graph. It is generated from the exact composition candidate.

```text
TAI roots
→ registry validation
→ dependency closure
→ dependency-before-dependent order
→ profile closure
→ per-block lifecycle gaps
→ realization-selection gaps
→ five-surface evidence gaps
→ canonical roadmap digest
```

For each composed block, the roadmap emits only unresolved work:

| Observed state | Generated work |
|---|---|
| `DISCOVERED` | identify → qualify → admit → activate |
| `IDENTIFIED` | qualify → admit → activate |
| `QUALIFIED` | admit → activate |
| `ADMITTED` | activate |
| `ACTIVE` | no lifecycle work |
| `DEPRECATED` | reactivate |
| `RETIRED` or `ARCHIVED` | refuse target; do not silently reactivate |
| no selected realization | select passport-bound realization |
| evidence standing below `ALIVE` | close all five evidence surfaces |

The dependency closure therefore generates the rebuilding roadmap. The roadmap does not merely describe the blocks.

### TAI rebuild simulation

A Target Architecture Instance is defined by:

- stable target identity;
- root GBB identities;
- required profile closure;
- optional expected composition digest.

A rebuild receipt may be issued only when the generated roadmap has zero unresolved steps. The bounded simulation binds candidate identity, target identity, exact composition digest, dependency-before-dependent reconstruction order, profile closure, admitted evidence digests per block, resulting `ALIVE` standing, and canonical BLAKE3 receipt digest.

No external infrastructure is actuated by this kernel. The receipt proves the bounded reconstruction simulation, not production deployment.

## Five cumulative credentials

### GBB-100 — Foundation

**Outcome:** preserve the fence and diagnose the calculus.

The candidate must:

1. explain identity, lifecycle, standing, ports, ceilings, obligations, exclusions, and provenance without collapsing them;
2. run validation and map malformed cases to stable refusal codes and bounded repairs.

Artifacts:

- `ggen.building-block.boundary-analysis.v1`;
- `ggen.building-block.diagnostic-report.v1`.

### GBB-200 — Builder

**Outcome:** manufacture one independently verifiable Building Block.

The candidate must:

1. construct a valid block with typed ports, contract, ceilings, exclusions, provenance, and passport-bound realization;
2. close every evidence obligation through all five proof surfaces and derive `ALIVE` mechanically.

Artifacts:

- `ggen.building-block.v1`;
- `ggen.building-block.evidence-bundle.v1`.

### GBB-300 — Composer

**Outcome:** manufacture architecture from dependency closure rather than a hand-authored implementation sequence.

The candidate must:

1. compose selected roots into deterministic dependency-before-dependent order and emit the canonical composition receipt;
2. refuse duplicate identities, missing dependencies, dependency cycles, and incompatible profiles without deleting constraints.

Artifacts:

- `ggen.building-block.receipt.v1`;
- `ggen.building-block.composition-refusal.v1`.

### GBB-400 — Governor

**Outcome:** preserve architecture law while realizations and lifecycle change.

The candidate must:

1. assess substitution while preserving promised outputs, passport binding, authority ceilings, and resource ceilings;
2. govern activation, deprecation, retirement, standing, and broker-addressed intents as distinct states.

Artifacts:

- `ggen.building-block.substitution-assessment.v1`;
- `ggen.building-block.governance-report.v1`.

### GBB-500 — TAI Manufacturer

**Outcome:** use GBBs as generators of the exact reconstruction roadmap and simulate rebuilding the complete Target Architecture Instance.

The candidate must:

1. generate the deterministic rebuild roadmap from current GBB and evidence state;
2. resolve every roadmap step and issue a replay-stable TAI rebuild receipt;
3. inject one dependency, profile, realization, evidence, or replay failure and recover without bypassing law;
4. manufacture a verifier and falsifier fixture another candidate can replay independently.

Artifacts:

- `ggen.building-block.rebuild-roadmap.v1`;
- `ggen.building-block.tai-rebuild-receipt.v1`;
- `ggen.building-block.recovery-receipt.v1`;
- `ggen.building-block.transfer-verifier.v1`.

## Crown size

The first program contains twelve cumulative requirements. Each requirement requires five proof surfaces.

```text
12 requirements × 5 proof surfaces = 60 certification proof surfaces
```

The primary manufactured artifact is additionally bound into each requirement receipt. It is not counted as a sixth proof surface because it is the object tested by the five surfaces.

## Assessment mechanics

Each assessment runs against an exact repository SHA and an admitted fixture. The candidate may use automation, code generation, local models, agents, or ggen packs. Tool restriction is not the competency. Lawful manufacturing is.

The candidate fails a requirement when any of these occurs:

- a required proof surface is absent;
- a digest is empty or detached from its requirement;
- a negative fixture is accepted;
- replay changes canonical output;
- authority or resource scope expands;
- a dependency or profile constraint is silently removed;
- a roadmap is hand-authored outside the observed GBB closure;
- a TAI receipt is issued with unresolved roadmap work;
- direct actuation occurs from the architecture kernel.

## Delivery model

CertificationAssist decomposes the program into objectives, detects Triple Darkness, manufactures practice probes, runs deterministic self-play, and records evidence candidates.

In examination mode, the candidate receives an admitted registry and TAI target. The target may contain incomplete lifecycle, missing realization selection, partial evidence, composition faults, or a candidate substitution.

The required execution path is:

```text
parse
→ route
→ admit/refuse
→ diagnose/repair
→ compose
→ generate roadmap
→ simulate rebuild
→ verify receipt
→ replay
```

An independent verifier reruns the positive and negative fixtures and binds its result to the exact source, target, program version, and artifact digests. The award is a deterministic cumulative receipt. A badge or certificate is only a projection of that receipt.

## Renewal and version deltas

Certification does not expire merely because time passed. It becomes stale when the governing law or target capability changes materially.

```text
previous requirement closure
+ changed/new requirements
+ replay of affected prior requirements
→ renewed award receipt
```

Unchanged, replay-stable requirements are not repeated for ceremony.

## Verification ladder

1. **unit** — requirement closure, missing-surface refusals, roadmap state transitions;
2. **integration** — registry composition feeding roadmap generation;
3. **end to end** — complete TAI rebuild receipt;
4. **chaos** — retired block, missing profile, missing evidence, or invalid graph refusal;
5. **stress** — bounded large-registry roadmap generation;
6. **benchmark** — deterministic generation cost and receipt stability;
7. **verifier report** — exact-head workflow result and published receipts.
