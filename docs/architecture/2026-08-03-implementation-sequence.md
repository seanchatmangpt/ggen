# Ecosystem Implementation Sequence

**Purpose:** convert the target architecture into the shortest defensible path to one cross-repository `ALIVE` crown.

## 1. Sequence rule

Do not expand catalog breadth until one complete vertical composition is independently replayable.

The required sequence is:

```text
canonical identity
→ shared contracts
→ portable toolchain
→ normalized receipt DAG
→ reference product
→ independent replay
→ ecosystem crown
```

## 2. Workstream 1 — Canonical ecosystem capability registry

### Objective

Manufacture one canonical identity graph that reconciles capability catalogs across ggen Vision 2030, ggen SBB, ggen-legacy, CNS, Ferroplan, DTeam, KNHK, MCPP, GitVan, ByteStar, and selected domain repositories.

### Required outputs

- canonical capability URI and stable identifier;
- labels, aliases, and deprecation relations;
- ABB requirements and acceptance laws;
- repository realization edges with exact source coordinates;
- dependency and substitution relations;
- authority owner and claim ceiling;
- supported, blocked, unsupported, and retired dispositions;
- capability passport projection.

### Admission tests

- every selected capability resolves to exactly one canonical identity;
- aliases do not create duplicate capability subjects;
- every realization names repository, ref or exact SHA, and implementation path;
- no realization self-certifies aggregate standing;
- substitution requires explicit law and verifier evidence;
- unresolved collisions remain typed conflicts rather than arbitrary merges.

### Standing target

`PARTIAL_ALIVE` when the graph validates and projects deterministically. `ALIVE` only when at least one realized capability passport executes and independently replays.

## 3. Workstream 2 — Shared Doctor, Wizard, Telco, and Truthforge contracts

### Objective

Extract shared ontology and protocol identity while preserving repository-native implementation bodies.

### Contract boundaries

#### Doctor

Input: exact subject plus observation authority.  
Output: findings, evidence references, claim ceiling, and optional repair intent.  
Authority: observation and diagnosis only.

#### Wizard

Input: admitted requirements and findings.  
Output: reversible plan, alternatives, cost and authority bounds, and BRCE intent.  
Authority: construction only.

#### Telco

Input: typed payload plus subject, authority, correlation, and receipt parent.  
Output: delivered envelope or typed transport refusal.  
Authority: transport only.

#### Truthforge

Input: exact evidence graph, witness outcomes, falsifiers, and replay request.  
Output: independent verdict, claim ceiling, and standing.  
Authority: verification only.

### Required compatibility rule

Implementations may differ internally, but shared contract projections must preserve semantic identity for required fields, refusal types, and receipt bindings.

### Standing target

`ALIVE` for each contract only after two independent repository implementations exchange and replay one real envelope without schema-specific adapters hidden outside the declared compatibility layer.

## 4. Workstream 3 — Universal offline Rust Toolchain Capsule

### Objective

Remove the highest-frequency blocker by manufacturing a portable, offline-capable Rust execution boundary.

### Capsule identity

```text
pinned Rust toolchain
+ target set
+ dependency cache
+ source capsule
+ validation pack
+ execution mode
→ portable receipt DAG
```

### First consumers

1. DTeam
2. wasm4pm-compat
3. KNHK
4. MCPP
5. NASA Rust core
6. Unibit

### Required evidence

- toolchain version and component digests;
- target triples;
- dependency cache manifest and digests;
- offline invocation command;
- source identity;
- compile and test receipts;
- deliberate missing-toolchain or corrupted-cache refusal;
- replay on at least two bounded consumer subjects.

### Standing target

`PARTIAL_ALIVE` after one consumer compiles offline. `ALIVE` after two independent consumers reproduce their expected consequences and receipt DAGs with the same admitted capsule identity.

## 5. Workstream 4 — Receipt DAG normalization

### Objective

Replace weak result-hash receipts with operation-bound receipt edges.

### Required edge law

```text
subject
+ authority
+ plan
+ resolved arguments
+ prior edge
+ grant
+ result or observed consequence
→ receipt edge
```

### Migration strategy

- define receipt DAG v2 as canonical;
- provide explicit v1 compatibility adapters;
- mark information lost during v1 adaptation;
- prohibit adapted v1 receipts from proving claims that require missing authority or consequence fields;
- add chain-order, argument, authority, and consequence mutation falsifiers;
- export OCEL-compatible event identity.

### Admission tests

- changing resolved arguments changes the edge digest;
- changing authority changes the edge digest;
- changing parent topology changes the edge digest;
- result-only hashes cannot be promoted to consequence receipts;
- replay detects removed, reordered, duplicated, or substituted edges;
- independent verifier recomputes the crown digest.

### Standing target

`ALIVE` for a bounded v2 receipt DAG after exact replay and mutation refusal. Existing repositories remain `PARTIAL_ALIVE` until migrated or explicitly bounded behind adapters.

## 6. Workstream 5 — Cross-repository reference product

### Selected path

```text
CNS request
→ Ferroplan construction
→ ggen manufacture
→ BRCE local consequence
→ wasm4pm OCEL and conformance
→ ggen-legacy independent replay
```

### Why this path

It uses bounded subjects that already have strong local evidence and avoids physical-device, production-service, and unavailable external package dependencies.

### Reference scenario

A canonical capability request selects a CNS capability, Ferroplan constructs an admitted plan, ggen manufactures a local projection, BRCE performs one bounded filesystem or local-process consequence, wasm4pm records the object-centric event and receipt topology, and ggen-legacy independently reconstructs and verifies the claim.

### Required evidence package

- exact repository and source identities;
- canonical capability passport;
- Doctor findings;
- Wizard plan;
- Telco envelopes;
- BRCE intent and grant;
- result and consequence receipts;
- OCEL export;
- independent replay report;
- mutation portfolio;
- scoped standing ledger.

### Falsifiers

- altered capability identity;
- unauthorized plan substitution;
- changed resolved argument;
- direct actuation bypassing BRCE;
- missing result or consequence receipt;
- reordered receipt edge;
- altered OCEL object relation;
- self-issued independent verdict;
- stale source SHA;
- replay under a different toolchain identity.

### Standing target

`ALIVE` for the exact bounded reference-product subject. This does not imply all repositories or production environments are `ALIVE`.

## 7. Workstream 6 — MMDIO authority reconciliation

### Objective

Resolve the divergence between the ggen MMDIO pack and the live MMDIO repository.

### Required decisions

- one canonical Mermaid type registry;
- one owner for parser and grammar admission;
- generated consumer adapters;
- specialized renderers for syntax-heavy types;
- explicit `UNSUPPORTED` disposition for registered types without runtime closure;
- second-manufacture replay for generated models.

### Standing target

`ALIVE` for each diagram type only after parser, grammar, model projection, runtime render, and negative refusal execute against the exact admitted subject.

## 8. Workstream 7 — First ecosystem crown

### Crown predicates

The selected ecosystem slice may be crowned only when:

- every selected capability has a canonical passport;
- every dependency closes or is explicitly external;
- every consequential operation has a BRCE grant;
- every receipt edge verifies;
- every execution replays;
- every independent verdict is issued outside the implementation authority cycle;
- mutation controls fail as designed;
- generated projections reproduce under second manufacture;
- blocked and unsupported edges remain explicit;
- no local checkpoint is promoted to a broader crown.

### Crown output

```text
ecosystem-crown.json
standing-ledger.json
receipt-dag.json
ocel.json
independent-verifier-report.json
mutation-report.json
replay-report.json
```

## 9. Daily execution order

### Step 1

Create the canonical capability identity model and admit the first five cross-repository capabilities needed by the reference product.

### Step 2

Define shared Doctor, Wizard, Telco, and Truthforge contract schemas for only the fields required by the reference scenario.

### Step 3

Adopt receipt DAG v2 for the reference path and add compatibility adapters only where required.

### Step 4

Manufacture the offline Rust Toolchain Capsule in parallel with semantic work because it unblocks multiple downstream repositories but is not required for every local reference-product edge.

### Step 5

Execute the CNS → Ferroplan → ggen → BRCE → wasm4pm → ggen-legacy path with one bounded local consequence.

### Step 6

Run the mutation portfolio and independent replay. Repair only failed transitions; do not widen the scope.

### Step 7

Publish the exact bounded crown and list every excluded repository, device, service, runtime, and production edge.

## 10. Decision gates

| Gate | Required observation | Failure disposition |
|---|---|---|
| Capability identity | one canonical identity per selected capability | `REFUSED_CAPABILITY_COLLISION` |
| Authority | owner and claim ceiling resolve | `REFUSED_AUTHORITY_UNKNOWN` |
| Planning | deterministic admitted plan exists | `PARTIAL_ALIVE` or typed refusal |
| Manufacture | projection and second manufacture match | `REFUSED_GENERATED_DRIFT` |
| Actuation | valid BRCE grant precedes consequence | `REFUSED_UNRECEIPTED_ACTUATION` |
| Receipt | all required fields and parents verify | `REFUSED_RECEIPT_TOPOLOGY` |
| Process evidence | OCEL or equivalent event graph closes | `PARTIAL_ALIVE` |
| Independent replay | verifier recomputes expected standing | `UNKNOWN` or `REFUSED_SELF_CERTIFICATION` |
| Crown | all selected predicates close | `ALIVE` for exact subject only |

## 11. Highest-leverage next implementation

The highest-leverage implementation is the smallest complete reference-product slice, not another broad ontology expansion.

Start with five canonical capabilities:

1. capability admission;
2. plan construction;
3. deterministic manufacture;
4. brokered local consequence;
5. independent replay.

Use those five capabilities to prove the ecosystem architecture end to end. Expand only after the exact crown replays.
