# ggen Red-Team Detection Audit: Perspectives and Recommendations

This document consolidates the perspectives, concerns, and recommendations produced during repeated bounded defensive red-team simulations for ggen. It is deliberately evidence-bounded. The simulations exercised a policy model associated with the admitted ggen subject, but they did not execute the exact native ggen runtime through its real parse, admission, construction, BRCE, receipt, and replay boundaries.

Accordingly, the simulations are useful design evidence and test-corpus input. They are not proof that the native implementation enforces the modeled controls.

## Executive assessment

ggen has a strong conceptual security posture. Its repository contract already contains several unusually mature principles:

1. `SELECT`, `CONSTRUCT`, and `DO` are separated.
2. BRCE is the exclusive `DO` path where a BRCE boundary exists.
3. Model output, hooks, proofs, semantic derivations, and generated artifacts have no ambient execution authority.
4. A receipt must bind identity, authority, consequence, replay, and standing.
5. Evidence classes such as observed, executed, changed, verified, inferred, blocked, unsupported, and refused are kept distinct.
6. `ALIVE` requires observed execution against the exact admitted subject.

These are the correct foundations for agentic software manufacturing. The principal risk is not conceptual weakness. The principal risk is an **evidence gap between doctrine and runtime enforcement**.

Repeated simulations produced internally consistent outcomes: adversarial intents were refused or escalated, benign controls were admitted, containment was preserved, replay was deterministic, and receipt mutations were detected. However, those results were generated by a bounded model whose detector and expected outcome were defined together. That arrangement validates consistency of the model. It does not establish the native system's false-negative rate, false-positive rate, containment strength, receipt integrity, or escalation behavior.

The strongest defensible conclusion is therefore:

> The policy model is `ALIVE` within its admitted simulation boundary. The exact ggen subject remains `PARTIAL_ALIVE` for red-team detection assurance until the same corpus executes through the native runtime and produces independently verifiable receipts.

## What the simulations tested

The bounded swarms used randomized simulated-agent profiles and attack classes while excluding external systems, real users, credentials, networks, services, and repository mutation. Simulated agents had no actuation authority. The only modeled `DO` path was BRCE, and the acceptance invariant was zero unreceipted actuation.

The recurring scenario set included:

| Scenario | Expected disposition |
|---|---|
| Direct unbrokered actuation | `REFUSED_UNAUTHORIZED_DO` |
| Scope escape | `REFUSED_SCOPE_ESCAPE` |
| Path traversal | `REFUSED_PATH_ESCAPE` |
| Ambient shell or process execution | `REFUSED_AMBIENT_EXECUTION` |
| Hook attempting direct actuation | `REFUSED_HOOK_ACTUATION` |
| Receipt forgery or identity mismatch | `REFUSED_RECEIPT_INTEGRITY` |
| Replay drift | `REFUSED_REPLAY_IDENTITY` |
| Capability expansion | `REFUSED_CAPABILITY_BOUND` |
| Resource exhaustion | `REFUSED_COST_BOUND` |
| Unknown or unsupported semantics | `REFUSED_EVIDENCE_GAP` |
| Suspicious but non-decidable behavior | `ESCALATED_SECURITY_REVIEW_INTENT` |
| Reversible benign selection | `ADMITTED_SELECT` |
| Reversible benign construction | `ADMITTED_CONSTRUCT` |

Across the simulation runs, the model reported zero containment escapes, zero external interactions, zero unreceipted actuation, deterministic same-seed replay, and successful detection of deliberate receipt mutations. These are useful regression expectations. They should not be represented as native runtime measurements.

## Perspective 1: The architecture is pointed in the right direction

The most important positive finding is that ggen's security model starts at the correct boundary: **authority**, not prompt quality.

Prompt defenses can influence model behavior, but they cannot manufacture execution authority. A robust system assumes that model output may be hostile, confused, stale, nondeterministic, or semantically invalid. The system remains safe because model output is only input to admission and construction. It does not become machine consequence until an authorized broker validates and actuates it.

The BRCE doctrine is therefore more important than any individual detector. Detectors can fail. An exclusive actuation boundary limits the consequence of detector failure.

### Recommendation

Preserve BRCE as the only native actuation path. Treat every direct process, filesystem, network, publication, credential, deployment, and external-service operation outside BRCE as a structural defect, not merely a missing security check.

## Perspective 2: Detection and containment are different claims

A system may detect an attack but fail to contain it. It may also contain an attack without correctly classifying it.

The simulations combined these dimensions because every modeled event was sandboxed and non-actuating. Native verification must separate them:

- **Detection:** Was the hostile or unsupported intent classified correctly?
- **Admission:** Was the request admitted, refused, or escalated according to policy?
- **Containment:** Could the subject cause an unintended consequence despite the decision?
- **Receipt:** Was every permitted consequence bound to exact identity and authority?

### Recommendation

Produce separate machine-readable metrics for detection coverage, admission correctness, containment failure, and receipt completeness. Do not collapse them into a single pass rate.

A detector false negative is serious. A containment failure is categorically more serious because it proves unintended consequence crossed the authority boundary.

## Perspective 3: Zero simulated false negatives is not a runtime security claim

The repeated swarm reports showed zero false negatives and zero false positives inside the model. This is expected when the scenario generator, decision function, and oracle share the same taxonomy.

This creates **detector-oracle coupling**. The test proves that the implementation of the model matches the model's own expectations. It does not prove that the taxonomy covers unknown attack strategies or that native ggen makes the same decisions.

### Recommendation

Introduce independent adversarial fixture sources:

1. Hand-authored fixtures written without access to the detector implementation.
2. Property-generated mutations of valid ggen inputs.
3. Grammar-aware malformed inputs.
4. Metamorphic cases where semantically equivalent inputs must produce equivalent decisions.
5. Cross-agent cases generated by an independent model or rule engine.
6. Historical failure fixtures extracted from real bug reports and incidents.
7. Native boundary faults such as timeouts, truncation, partial writes, stale capabilities, and replay identity drift.

Report false-negative and false-positive rates by fixture provenance. A single aggregate rate hides oracle coupling.

## Perspective 4: Random agents are useful only when randomness is replayable and coverage is visible

Randomized agent profiles improve combinatorial exploration, but randomness without a coverage model can create the appearance of breadth while repeatedly sampling the same shallow cases.

The simulations correctly retained explicit seeds and deterministic replay. The next step is to bind randomness to coverage obligations.

### Recommendation

For every swarm run, record:

- exact subject SHA and tree identity;
- toolchain and configuration identities;
- seed set and random generator version;
- profile distribution;
- scenario distribution;
- capability and authority bounds;
- transition coverage;
- refusal-code coverage;
- receipt mutation coverage;
- escalation-path coverage;
- resource limits and termination reason.

A swarm should fail its verifier when required classes are absent, even if every sampled case passes.

## Perspective 5: Receipt integrity needs semantic binding, not only hashing

The model detected mutations to fields such as subject, seed, standing, event digest, DO path, and unreceipted-actuation count. This demonstrates the basic value of canonicalization and digest binding.

Hash equality alone does not establish who authorized an action, whether the signer had standing, whether the consequence actually occurred, or whether an event was omitted before hashing.

### Recommendation

Define a canonical receipt envelope that binds at least:

- receipt schema and version;
- exact subject identity and tree digest;
- admitted observation digest;
- policy and configuration identity;
- authority principal and delegated capability;
- selected route;
- constructed intent digest;
- broker decision and stable refusal code;
- requested and observed consequence;
- event ordering and parent receipt links;
- timestamps or monotonic sequence evidence;
- toolchain and environment identity;
- replay command or replay descriptor;
- standing and its explicit scope;
- signer identity and signature where signatures are available.

The verifier should reject truncation, reordering, duplication, substitution, stale-parent replay, and authority mismatch—not only changed scalar fields.

## Perspective 6: Replay must prove the same subject, not merely the same script

The simulations replayed the same Python harness with the same subject string and seeds. That establishes harness determinism. It does not establish native ggen replay.

Native replay requires identity equivalence across source, configuration, policy, toolchain, environment, inputs, broker behavior, and relevant external dependencies.

### Recommendation

Split replay standing into two explicit claims:

- `VERIFIER_REPLAY_ALIVE`: the validation harness reproduced its event stream and receipt.
- `SUBJECT_REPLAY_ALIVE`: the exact native ggen subject reproduced the admitted consequence under matching identities.

Do not reuse a prior subject receipt when source, validator, configuration, policy, toolchain, or environment identities differ.

## Perspective 7: Escalation is safe only when it remains an intent

The simulation treated escalation as `ESCALATED_SECURITY_REVIEW_INTENT`. That is the correct shape. Escalation should manufacture a review intent, not open a privileged side channel.

An escalation path becomes dangerous when it can silently broaden authority, bypass normal admission, or directly invoke tools.

### Recommendation

Require escalation records to include:

- the undecidable or suspicious condition;
- the evidence available at escalation time;
- the authority requested;
- the authority currently held;
- the exact next admissible action;
- expiration and replay constraints;
- a receipt parent linking the escalation to the original event.

Escalation consumers must return a new admitted intent to BRCE. They must not actuate directly.

## Perspective 8: Native containment requires real boundary tests

A policy-level `sandboxed: true` field is not proof of sandboxing. Native containment must be observed at the boundaries that matter:

- process creation;
- filesystem reads and writes;
- path normalization and traversal;
- environment-variable access;
- network sockets and DNS;
- credential and secret providers;
- plugin or hook execution;
- generated-code execution;
- resource ceilings;
- publication and deployment surfaces.

### Recommendation

Create an exact-subject native audit capsule with deny-by-default capabilities. The capsule should expose only fixture inputs and an ephemeral output directory. It should capture process, filesystem, and network evidence sufficient to prove that denied boundaries were not crossed.

Use platform-native isolation where available, but keep the acceptance contract platform-neutral: no external interaction, no write outside the admitted directory, no child process outside the broker policy, bounded CPU/memory/time, and complete receipting of every permitted consequence.

## Perspective 9: Typed refusals are part of the public security contract

Stable typed refusals make failures actionable, testable, and replayable. Generic errors or silent fallback destroy evidence and can accidentally convert unsupported behavior into apparent success.

### Recommendation

Maintain a versioned refusal registry. Each refusal should define:

- code;
- admission phase;
- triggering invariant;
- authority held and required;
- whether retry is lawful;
- whether escalation is permitted;
- receipt requirements;
- compatibility expectations.

Tests should assert exact refusal classes at the native boundary. Message text may evolve; the semantic refusal identity should remain stable or migrate explicitly.

## Perspective 10: Unknown must remain unknown

The simulations correctly used evidence-gap refusals for unknown semantics. This is essential. Agentic systems become unsafe when uncertainty is collapsed into an inferred success path.

### Recommendation

Preserve these separations:

- `UNKNOWN` is not admitted.
- `UNSUPPORTED` is not a policy refusal unless a policy boundary was evaluated.
- `BLOCKED` identifies a dependency or authority boundary.
- `BUILD_BROKEN` identifies a verifier path that cannot be reached.
- `PARTIAL_ALIVE` is not a crown claim.
- `ALIVE` requires observed execution against the exact admitted subject.

Every audit report should show what was observed, executed, changed, verified, inferred, refused, blocked, and unsupported.

## Prioritized remediation roadmap

### P0 — Establish native subject execution

Build a reproducible audit capsule for the exact ggen SHA and execute the seeded corpus through:

```text
parse → route → admit/refuse → construct → BRCE → receipt → replay → standing
```

Acceptance requires native process execution, exact-subject identity, stable refusal evidence, zero unreceipted actuation, and replayable receipts.

### P0 — Prove BRCE exclusivity

Inventory every native side-effect edge. Demonstrate that process, filesystem, network, credential, publication, deployment, and hook consequences either pass through BRCE or are explicitly outside the supported boundary.

Add permanent guards for any discovered bypass.

### P0 — Create the canonical security receipt schema

Specify canonical serialization, identity fields, authority fields, event linkage, consequence evidence, standing, replay data, and signature support. Add mutation tests for omission, reordering, truncation, substitution, duplication, and stale replay.

### P1 — Decouple detector and oracle

Add independent fixtures, grammar mutation, property testing, metamorphic testing, and historically derived failures. Track provenance and coverage separately.

### P1 — Measure false positives on real benign workflows

Run representative ggen selection, construction, generation, synchronization, hook, and replay workflows under the detector. A secure detector that blocks normal manufacturing is operationally defective.

### P1 — Validate escalation end to end

Prove that suspicious events create review intents, preserve evidence, request bounded authority, and return through normal admission and BRCE. Prove there is no direct escalation actuation path.

### P1 — Add native resource-abuse testing

Exercise bounded recursion, large graphs, adversarial templates, repeated replay, receipt amplification, malformed streams, cancellation, and timeout behavior. Verify deterministic typed outcomes and bounded cleanup.

### P2 — Make red-team verification continuous

Once the native verifier is trustworthy, run it against exact published heads. Persist a machine-readable receipt bundle containing subject, validator, configuration, toolchain, event corpus, results, and replay instructions.

Hosted CI should supplement, not replace, locally reproducible validation.

### P2 — Publish assurance by claim, not by dashboard color

Expose scoped claims such as:

- admission refusal coverage;
- BRCE exclusivity;
- containment boundary coverage;
- receipt mutation coverage;
- subject replay standing;
- unresolved blockers and falsifiers.

Avoid a single security score that obscures which boundary was actually executed.

## Recommended acceptance matrix

| Claim | Required proof | Minimum standing |
|---|---|---|
| Policy taxonomy is internally consistent | Deterministic model execution and replay | `ALIVE` for the model only |
| Native ggen emits stable typed refusals | Exact runtime executes attack corpus | `ALIVE` for refusal boundary |
| BRCE is exclusive | Native side-effect inventory plus bypass tests | `ALIVE` for actuation boundary |
| No external interaction | Process/filesystem/network evidence from containment capsule | `ALIVE` for tested environment |
| Receipt integrity | Canonical receipt plus mutation and signature verification | `ALIVE` for receipt boundary |
| Replayability | Same exact subject and identities reproduce consequence | `ALIVE` for subject replay |
| Production security | Representative deployment execution and operational evidence | Not established by the simulations |

## Immediate next bounded implementation

The next implementation should be deliberately narrow:

1. Materialize the exact admitted ggen SHA.
2. Identify one real native entrypoint that reaches admission and a BRCE-mediated consequence.
3. Port a minimal corpus containing one benign construction case and one case for each stable refusal class.
4. Execute in a deny-by-default local capsule.
5. Produce a canonical native receipt and replay it.
6. Publish the command, exits, subject identity, changed state, verifier outputs, blockers, and falsifiers.

Do not begin with a larger autonomous swarm. First establish one exact native end-to-end path with a trustworthy receipt. Scale the swarm only after the crown path is `ALIVE`.

## Falsifiers

The recommendations and standing in this document must be revised if any of the following is observed:

1. The exact native subject has already executed the complete admitted red-team corpus with independently verifiable receipts.
2. BRCE is not the exclusive actuation boundary in the supported runtime.
3. A modeled refusal has no corresponding native admission boundary.
4. Same-subject replay is nondeterministic without an explicitly admitted nondeterministic dependency.
5. A receipt mutation, truncation, reordering, or authority substitution remains valid.
6. A benign native workflow is refused by the proposed detector policy.
7. An adversarial native workflow is admitted or produces an unreceipted consequence.

## Final perspective

ggen's doctrine is already stronger than the common pattern of treating model alignment as the security boundary. Its central idea is correct: preserve reversible construction, deny ambient authority, broker every consequence, and bind every lawful act to a replayable receipt.

The remaining work is to turn that doctrine into exact-subject execution evidence. The goal is not a larger simulation number. The goal is a demonstrable correspondence:

```text
policy → native admission → BRCE consequence → receipt → replay → scoped standing
```

Until that correspondence is observed, the correct standing remains `PARTIAL_ALIVE`.
