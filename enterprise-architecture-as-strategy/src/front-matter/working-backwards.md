# The Working-Backwards Promise

The launch promise is simple:

> A material enterprise change can be evaluated, manufactured, governed, and evidenced from one admitted architecture graph.

A user begins with a proposed change: introduce a shared customer identity, replace a message broker, publish an external capability pack, move a regulated workload across regions, retire an ontology version, or reorganize a portfolio around reusable platforms.

The system answers five classes of questions.

## Strategy

- Which operating-model decision motivates the change?
- Which capabilities and value streams are affected?
- Which target-state principle does the change advance?
- What measurable benefit is expected?

## Architecture

- Which business, data, application, and technology building blocks participate?
- What is the baseline state?
- What transition architectures are available?
- Which dependencies, standards, and constraints apply?

## Delivery

- Which packs, plans, templates, policies, schemas, tests, workflows, and migrations must be manufactured?
- What work can proceed in parallel?
- Which checkpoints gate later work?
- What is the bounded write and execution authority?

## Operations

- What capacity, reliability, security, cost, observability, and support obligations follow?
- Which runtime signals prove or disprove correspondence?
- What should trigger repair, rollback, deprecation, or architecture change?

## Evidence

- Which claims have standing?
- Which remain unknown, partial, or unsupported?
- What receipts bind the observation, transformation, artifact, validation, and consequence?
- Can the outcome be replayed independently?

The promise is fulfilled only when these answers are linked by machine-traversable identity. A prose roadmap with no relationship to repository state does not satisfy it. A generated deployment with no relationship to business capability does not satisfy it. A formal proof with no correspondence to the runtime implementation does not satisfy it. A successful actuation with no receipt does not satisfy it.

The target product experience is summarized by one command:

```text
ggen architecture doctor
```

The command should explain what the architecture believes, why it believes it, what will change, what will be manufactured, what evidence is missing, what the expected operating envelope is, and what the next lawful transition can be.

This book describes the architecture required to make that command honest.
